## 1. Big Picture

The Full Details Questionnaire is a **5-stage AI-assisted interview** that a whistleblower goes through when filing a report. It does not ask static, pre-written questions. Instead, each stage is driven by a different AI or deterministic process that reads what the user has already written and adapts accordingly.

The stages in order:

```
Q1 (free narrative)
  → [AI Gap Detection] → Q2 (targeted follow-up, if a gap is found)
  → [LLM Sentence Synthesis] → [ChromaDB RAG Search]
  → Q3 (policy question with relevant excerpt shown)
  → Review & Submit
```

The whole pipeline is orchestrated by the frontend `FullDetailsQuestionnaire` component, which fires React hooks sequentially and advances steps as each hook resolves.

---

## 2. Terminology

| Term | Meaning |
|------|---------|
| **Q1** | The opening free-text narrative the reporter writes |
| **Q2** | The targeted follow-up question generated by the AI gap detection pipeline |
| **Q3** | The policy-contextualized question shown after the RAG retrieval step |
| **FQ1** | Frontend name for the Q2 step (Follow-up Question 1) |
| **Layer 1** | LLM-based structured extraction from Q1 text |
| **Layer 2** | Deterministic gap evaluation against Layer 1 output |
| **Layer 3** | Template lookup to generate the actual question text |
| **Constructed Sentence** | A short, factual LLM-generated summary of the full form used to improve RAG retrieval |
| **RAG** | Retrieval-Augmented Generation — vector similarity search against the policy PDF, then LLM re-ranking |
| **Gap** | A configurable rule that says "if the narrative is missing X, ask about it" |

## 3. User Journey Through the Questionnaire

The frontend step machine lives in `FullDetailsQuestionnaire.tsx`. The valid step transitions are:

```
q1
  → analyzing          (POST /questions/intake/analyze fires)
  → fq1                (if a follow-up question was returned)
  → constructing       (POST /rag/construct-sentence fires)
  → policyLoading      (POST /rag/policy-quote fires)
  → policyQuestion     (shows Q3 with policy excerpt)
  → review             (read-only summary, user confirms)
```

Every step that involves a network call has an **error path** with a "Skip" option — the questionnaire is designed to complete even if every AI step fails.

### State Machine Detail

| Step | What Happens | Hook Used |
|------|-------------|-----------|
| `q1` | User writes free narrative | — |
| `analyzing` | `useIntakeAnalysis` fires; shows spinner | `useIntakeAnalysis` |
| `fq1` | AI-generated follow-up question shown | — |
| `constructing` | `useConstructedSentence` fires; shows spinner | `useConstructedSentence` |
| `policyLoading` | `usePolicyQuote` fires; shows spinner | `usePolicyQuote` |
| `policyQuestion` | Policy excerpt + hardcoded Q3 prompt shown | — |
| `review` | Read-only Q&A summary | — |

## 4. Layer 1 — LLM Extraction

**File:** `backend/app/question_processors/intake_processor.py`  
**Endpoint:** `POST /questions/intake/analyze`

Layer 1 reads Q1 and uses Gemini to extract a structured JSON object. Think of it as asking the LLM: "parse this incident narrative into a set of boolean flags and entity lists."

### Input

```json
{
  "q1_text": "My manager has been systematically excluding me from meetings...",
  "form_data": {
    "general_nature": "Workplace Harassment",
    "where_occurred": "London Office",
    "when_occurred": "Last 3 months",
    ...
  }
}
```

The optional `form_data` (already filled-in form fields) is appended to the prompt as **disambiguating context** — it helps the LLM avoid asking for information the reporter already provided in other form fields.

### Output Schema (`Layer1Result`)

```python
{
  "summary":                  str,    # 2-4 sentence neutral summary
  "dates_mentioned":          list,   # explicit dates in narrative only
  "people_mentioned":         list,   # explicitly named individuals
  "locations_mentioned":      list,   # explicit place names
  "specific_examples_present": bool,  # true if ≥1 concrete event described
  "evidence_described":       bool,   # true if docs/emails/screenshots mentioned
  "timeline_clear":           bool,   # true if sequence of events reconstructible
  "allegation_type":          list,   # e.g. ["harassment", "discrimination"]
  "length_character_count":   int,    # actual character count (set in Python, not trusted from LLM)
  "_used_defaults":           bool    # true if LLM failed and fallback values were used
}
```

### Fallback Behaviour

If the LLM returns invalid JSON or an empty response, the processor sets `_used_defaults = True` and fills in safe defaults (empty arrays, `False` booleans). Layer 2 detects this flag and **skips gap evaluation entirely**, so a broken LLM call never surfaces a nonsense follow-up question.

## 5. Layer 2 — Deterministic Gap Analysis

**File:** `backend/app/question_processors/intake_processor.py` — `IntakeLayer2`  
**No LLM involved.** Pure Python logic.

Layer 2 takes the Layer 1 JSON and evaluates a prioritised list of **gap rules** against it. It returns **at most 1 gap** — whichever rule has the highest priority (lowest number) that evaluates to `True`.

### Gap Rule Schema

```python
{
  "id":       "no_witnesses_mentioned",     # unique slug
  "label":    "No Witnesses Mentioned",     # human-readable
  "priority": 2,                            # 1 = highest
  "active":   True,
  "criteria": {
    "type":      "boolean_false",           # see below
    "field":     "witnesses_mentioned",     # key in Layer1Result
    "threshold": None                       # only for length_threshold type
  },
  "template": "Was anyone else present..."  # question text
}
```

### Criteria Types

| Type | Fires when... |
|------|--------------|
| `boolean_false` | `Layer1Result[field] == False` |
| `empty_array` | `Layer1Result[field] == []` |
| `length_threshold` | `Layer1Result[field] < threshold` |

### Form-Field Suppression

The `_FORM_FIELD_GAP_SUPPRESSION` map in `intake_processor.py` is an extension point that lets a filled form field suppress a gap. It is currently empty: the surviving gap pool is evaluated against the combined narrative (`full_details_q1` + `sequence_of_events` + `evidence_description`), which already captures all standardised input, so no suppression rules are needed at present.

### Default Gap Set (in priority order)

| Priority | Gap ID | Field Checked | Condition |
|----------|--------|---------------|-----------|
| 1 | `no_specific_example` | `specific_examples_present` | is `False` |
| 2 | `no_witnesses_mentioned` | `witnesses_mentioned` | is `False` |
| 3 | `no_prior_reporting` | `prior_reporting_mentioned` | is `False` |
| 4 | `no_impact_described` | `impact_described` | is `False` |
| 5 | `no_retaliation_context` | `retaliation_mentioned` | is `False` |

Sequence-of-events and evidence coverage are handled up front as **standardised questions** in the wizard (Q2 and Q3), so they no longer need a gap template. Date / location / named-individual gaps were dropped because the main form already captures those fields (`when_occurred`, `incident_location`, `where_occurred`, `person_1..10`).

All gaps are configurable via the Admin panel and persisted in `backend/data/settings.json`.

## 6. Layer 3 — Question Template Selection

**File:** `backend/app/question_processors/intake_processor.py` — `IntakeLayer3`

Layer 3 is trivial: for each gap identified by Layer 2, it looks up the `template` string from that gap's config and returns it as the follow-up question. Since Layer 2 returns at most 1 gap, Layer 3 returns at most 1 question.

### API Response Shape

```json
{
  "extraction": { ...Layer1Result },
  "gaps": ["no_witnesses_mentioned"],
  "follow_up_questions": [
    {
      "gap_id": "no_witnesses_mentioned",
      "question_text": "Was anyone else present who could corroborate what you've described — witnesses or people who saw or heard the incident?"
    }
  ]
}
```

The frontend persists the latest successful response (plus a client timestamp and `used_defaults`) to **`sessionStorage`** under `whistleblow_lastIntakeAnalysis` so the Analysis page can show it in the same browser session without re-running the pipeline.

## 7. Q2 — The AI-Generated Follow-Up Question

**Q2 is the user-facing label for the output of Layers 1–3.**

The follow-up question text (from Layer 3 template) is shown to the user in the `fq1` step. The user's answer is stored in `report.full_details_q2`. The question text itself is stored in `report.full_details_q2_question`.

**If no gap is identified** (i.e., the narrative already covers everything), the `fq1` step is **skipped entirely** and the wizard moves straight to the `constructing` step.

> Note: There are also legacy endpoints `POST /questions/q2/generate` and `POST /questions/q3/generate` in `backend/app/routers/questions.py` that call separate processor classes (`q2_processor.py`, `q3_processor.py`). These are currently **dead code** — the active pipeline runs through `POST /questions/intake/analyze` instead.

## 8. Constructed Sentence Builder

**File:** `backend/app/rag/sentence_builder.py`  
**Endpoint:** `POST /rag/construct-sentence`  
**Hook:** `useConstructedSentence`

Before querying the policy database, the system builds a **single factual summary sentence** (1–3 sentences in practice) from the entire form. The purpose: a naive concatenation of field values produces noisy, repetitive retrieval queries. A synthesized sentence is a cleaner semantic signal.

### Process

1. Pulls the following fields from `form_data` (skips empties):
   - `general_nature`, `where_occurred`, `when_occurred`, `duration`
   - `full_details_q1`, `full_details_q2`, `incident_location`
   - `is_employee`, `supervisor_involved`, `management_aware`
   - `how_aware`, `persons_concealing`, `allegation_type`

2. Formats them into a structured prompt and calls Gemini at **temperature=0.2** (near-deterministic) with rules:
   - Do not include reporter PII
   - No speculation — only what was stated
   - Write in third person, past/present tense
   - Output: 1–3 factual sentences only

3. **Fallback on failure:** concatenates `Q1 + Q2 + general_nature + where_occurred`, truncated to 500 chars.

The result is stored in `report.constructed_sentence` and passed to the RAG pipeline.

## 9. RAG Pipeline — Policy Quote Retrieval

**File:** `backend/app/rag/service.py`  
**Endpoint:** `POST /rag/policy-quote`  
**Hook:** `usePolicyQuote` (8-second timeout)

### Step-by-Step

**Step 1 — Embedding**  
The constructed sentence is embedded using `gemini-embedding-001` into a vector.

**Step 2 — Vector Search**  
ChromaDB searches the `whistleblowing_policy` collection (the ingested policy PDF, chunked with section metadata). Returns top 5 candidates with similarity scores. Candidates with similarity < 0.3 are discarded.

Each chunk in ChromaDB has metadata:
```json
{
  "section_title": "Reporting Channels",
  "chapter": "3",
  "page": 12,
  "type": "body"
}
```

**Step 3 — LLM Re-Ranking**  
The top candidates are passed to Gemini for relevance scoring (1–5). Candidates scoring below 3 are filtered out. The top scorer is selected.

**Step 4 — Quote Extraction**  
From the top candidate, the LLM extracts a verbatim short quote from the chunk text.

**Step 5 — Response**
```json
{
  "quote": "Employees are encouraged to report concerns through the designated whistleblowing channel...",
  "section": "Reporting Channels — Page 12",
  "similarity": 0.74,
  "relevance_score": 4
}
```

If all candidates score below threshold, returns `{ "quote": null, "section": null }` — the policy question step proceeds without showing an excerpt.

The quote and section are stored in `report.policy_quote_matched` and `report.policy_section_matched`.

## 10. Q3 — The Policy Question

Q3 is the final question before the review step. It is **not AI-generated** — the question text is hardcoded:

> "How well does this policy excerpt describe your experience?"

Canonical definition: `FULL_DETAILS_Q3_QUESTION` in `backend/app/prompts/display_content.py` and `frontend/src/constants/policyQuestion.ts` (keep in sync).

What is AI-powered is the **context shown alongside it**: the retrieved policy excerpt from Step 9, displayed in a blockquote with its section citation.

The user's answer goes into `report.full_details_q3`. The question text is stored in `report.full_details_q3_question`.

If no policy excerpt was retrieved (RAG returned null), the question is still shown — just without the excerpt block.

## 11. Report Data Model

**File:** `frontend/src/types/report.ts`

The full report object is a flat TypeScript interface that covers all form stages. The fields added by the Full Details pipeline are:

```typescript
// User-written answers
full_details_q1: string           // Opening narrative
full_details_q2: string           // Answer to AI-generated follow-up
full_details_q3: string           // Answer to policy question

// AI-generated question text (stored for audit/display)
full_details_q2_question: string  // Text of the gap question that was asked
full_details_q3_question: string  // Always: "How well does this policy excerpt describe your experience?"

// Pipeline outputs (stored for traceability)
policy_quote_matched: string      // Verbatim policy excerpt
policy_section_matched: string    // "Section Title — Page X"
constructed_sentence: string      // LLM synthesis used for RAG query
```

The `ReportContext` (React Context) holds a single `ReportData` object and exposes `updateReport(Partial<ReportData>)`. Every pipeline step writes its outputs into this context so they are available globally.

## 12. The Analysis Page

**Route:** `/analysis`  
**File:** `frontend/src/pages/AnalysisPage.tsx`

This is a **read-only diagnostic page**. It shows the result of the most recent intake analysis and the current gap configuration. Its audience is admin/investigator users who want to understand what the AI detected in a submission.

### Section 1: Last Analysis Result

Reads the stored intake payload from **session storage** (written by `useIntakeAnalysis` after a successful `POST /api/questions/intake/analyze`) and loads gap definitions from **`GET /api/intake/gaps`**. It renders three cards:

**Layer 1 Card — Extraction Data**
- Summary text
- Character count
- Boolean flags displayed with colored badges: `timeline_clear`, `specific_examples_present`, `evidence_described`
- Entity lists: dates, people, locations, allegation types

**Layer 2 Card — Identified Gaps**
- Which gap(s) were triggered (by label and priority)
- What criteria matched
- A `GapStatusBadge` showing the actual value from Layer 1 that caused the gap to fire (e.g., `timeline_clear = False`)
- Warning if the gap ID no longer exists in config (i.e., it was deleted after this analysis ran)

**Layer 3 Card — Follow-Up Questions**
- The full question text that was presented to the user
- Tagged with the gap ID that generated it

### Section 2: Current Gap Configuration

Fetches `GET /admin/intake-gaps` and renders one expandable card per gap showing:
- Priority badge
- Label
- Criteria type badge (`bool` / `array` / `length`)
- Current value from the last analysis (if available) — so you can see "this gap fired because `timeline_clear` was `False`"
- The template question text

### Gap Status Badge Logic

The `GapStatusBadge` component reads the last Layer 1 extraction and shows the actual runtime value of the field being checked:

| Criteria Type | Value in L1 | Badge Shown |
|--------------|-------------|-------------|
| `boolean_false` | `True` | green "True" |
| `boolean_false` | `False` | red "False" |
| `empty_array` | non-empty | green "Present" |
| `empty_array` | `[]` | red "Not Present" |
| `length_threshold` | e.g. 450 | green/red "450 chars" |

## 13. Admin Configuration

**Route:** `/admin`  
**File:** `frontend/src/pages/AdminPage.tsx`

The Admin page exposes several controls relevant to the pipeline:

### Gap Configuration
- Full CRUD on the gap list (add, edit, delete, reorder)
- Reset to defaults
- Enable/disable individual gaps
- All changes are persisted immediately to `backend/data/settings.json` via file-locked writes

### Custom Prompt Templates
- Override the Q2/Q3 legacy prompt templates (for the dead-code endpoints — these do not affect the active pipeline)
- Custom policy excerpt text (fallback when RAG returns no result)

### AI Pipeline Diagnostics
- `POST /api/admin/test/ai-pipeline` — runs a 3-step sequential test
- 3 built-in fixtures: clear fraud, ambiguous report, edge case
- Test history persisted at `backend/data/test_history.json`

### Gemini Model Status
- Shows current active model and quota status
- Falls back through model chain: `gemini-2.5-flash-lite` is the most quota-tolerant

```
[User fills main form fields]
         │
         ▼
[Q1: Free narrative input]
         │
         ▼
POST /questions/intake/analyze
         │
    ┌────┴────────────────────────────────────────┐
    │          Layer 1: LLM Extraction             │
    │  Q1 text + form_data → structured JSON       │
    │  (summary, booleans, entity lists)            │
    └────┬────────────────────────────────────────┘
         │
    ┌────┴────────────────────────────────────────┐
    │         Layer 2: Gap Evaluation              │
    │  Pure Python: walk rules in priority order   │
    │  (up to 2 gaps that fire)                    │
    └────┬────────────────────────────────────────┘
         │
    ┌────┴────────────────────────────────────────┐
    │         Layer 3: Template Lookup             │
    │  Return question text for identified gap     │
    └────┬────────────────────────────────────────┘
         │
         ▼ sessionStorage (browser — last intake snapshot)
         │
[If follow-up question(s): show up to 2 gap questions to user]
[If no gap: skip to constructing]
         │
         ▼
POST /rag/construct-sentence
         │
    ┌────┴────────────────────────────────────────┐
    │      Gemini Synthesis (temp=0.2)             │
    │  All form fields → 1-3 sentence summary      │
    └────┬────────────────────────────────────────┘
         │
         ▼
POST /rag/policy-quote
         │
    ┌────┴────────────────────────────────────────┐
    │  1. Embed summary → vector                   │
    │  2. ChromaDB: top 5 chunks (sim ≥ 0.3)       │
    │  3. LLM re-rank: score 1-5, filter ≥ 3       │
    │  4. Extract verbatim quote from top chunk    │
    └────┬────────────────────────────────────────┘
         │
         ▼
[Q3: Show policy excerpt + hardcoded policy question]
         │
         ▼
[Review: all Q&A displayed, user submits]
         │
         ▼
[Full ReportData persisted / submitted]
```

## Key Design Decisions

**Why max 1 gap?**  
The system intentionally limits to the highest-priority gap rather than asking multiple follow-up questions. The rationale: a distressed whistleblower completing a sensitive form should not be interrogated. One targeted clarification is maximally useful with minimal friction.

**Why deterministic Layer 2?**  
Having an LLM decide "what is missing" introduces variability and hallucination risk. The deterministic layer ensures that gap logic is auditable, testable, and configurable by non-engineers via the Admin panel. The LLM's role is purely extraction (Layer 1), not judgment.

**Why a constructed sentence for RAG?**  
Form fields are structured (dropdowns, short strings). Q1 is a raw narrative. Naively concatenating them produces noisy, redundant query text. The synthesized sentence is a semantically clean single signal that outperforms field concatenation on embedding similarity.

**Why store question text alongside answers?**  
`full_details_q2_question` and `full_details_q3_question` are stored in the report so that the final submission is fully self-contained — a reviewer sees both question and answer without needing to re-run the pipeline.
